# Scaling Memcache at Facebook

This follows the same interview-preparation pattern as the previous Spanner analysis, and I’m keeping the technical claims **strictly grounded in the attached Facebook paper**. The paper describes how Facebook evolved a simple single-machine `memcached` implementation into a geographically distributed caching system handling **billions of requests per second and trillions of cached items**.


# 1. Executive Summary & Core Engineering Challenge

## What problem was Facebook solving?

Facebook's underlying persistent stores and backend services could not economically absorb the read traffic generated by its social-network workload.

The workload has two defining properties:

1. Users **consume roughly an order of magnitude more content than they create**, making it strongly read-heavy.
2. Reads come from heterogeneous sources including **MySQL, HDFS, and backend services**.

That made caching extremely valuable, but also meant the caching layer had to be generic.

The initial building block was extremely simple:

```text
memcached
    │
    └── Single-machine
        in-memory hash table

        get(key)
        set(key, value)
        delete(key)
```

Facebook turned that primitive into:

```text
                 Facebook Memcache
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
     Thousands       Multiple       Multiple
     of servers      clusters       regions
          │             │             │
          └─────────────┼─────────────┘
                        ▼
              Distributed Cache
                        │
                        ▼
               Persistent Storage
```

The challenge therefore wasn't simply:

> "How do we cache database results?"

It was:

> **How do we build a low-latency, fault-tolerant distributed cache capable of protecting backend storage while serving enormous read fan-out across thousands of servers, multiple clusters, and geographically distributed regions?**


## Scale

The production scale is the first thing worth remembering.

| Metric | Paper |
|---|---|
| Cache request rate                 | Billions/sec |
| Cached objects                     | Trillions    |
| Users served                       | >1 billion   |
| Typical popular-page fetches       | 521 items    |
| p95 fetches for that page          | 1,740 items  |
| Servers contacted by some requests | Hundreds     |
| Median memcache request latency    | 333 μs       |
| p75                                | 475 μs       |
| p95                                | 1.135 ms     |

The paper emphasizes that web pages routinely fetch **thousands of key-value pairs** from memcache.

This creates a very different problem from a conventional:

```text
Web Server → Cache → Database
```

because one user request can fan out to a huge number of cache servers.


# Core Engineering Challenges

Facebook organizes the architecture's evolution around **three scales**:

```text
                MEMCACHE EVOLUTION

                     Scale ↑
                       │
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼

   ONE CLUSTER     ONE REGION     MULTI-REGION

    Latency         Replication     Consistency
      +                 +               +
     Load          Failure domains   Replica lag
      +                 +
   Failures           Memory
```

This is probably the single best way to remember the paper.

### Scale 1 — Within one cluster

Main problems:

- Very high fan-out
- Network round trips
- Incast congestion
- Thundering herd
- Stale cache writes
- Cache interference
- Server failures

### Scale 2 — Multiple clusters inside one region

New problems appear:

- Duplicate cached data
- Memory inefficiency
- Cross-cluster network traffic
- Cache invalidation
- Cold-cache startup
- Smaller failure domains

### Scale 3 — Multiple geographic regions

The dominant new problem becomes:

> **Consistency.**

Replica databases may lag behind the master database, creating races between database replication and cache invalidation.


# 2. System Architecture & High-Level Design

# High-Level Architecture

The paper's Figure 2 shows the final evolution roughly as:

```text
                       MASTER REGION
                ┌────────────────────────┐
                │                        │
                │   Frontend Clusters    │
                │                        │
                │  ┌──────────────────┐  │
Users ─────────►│  │   Web Servers    │  │
                │  │        │         │  │
                │  │        ▼         │  │
                │  │    Memcache      │  │
                │  └──────────────────┘  │
                │           │            │
                │           ▼            │
                │    Storage Cluster     │
                │        MySQL           │
                └───────────┬────────────┘
                            │
                     Replication Stream
                            │
                            ▼
                ┌────────────────────────┐
                │     REPLICA REGION     │
                │                        │
                │   Frontend Clusters    │
                │                        │
                │   Web → Memcache       │
                │                        │
                │           │            │
                │           ▼            │
                │ Read-only DB replicas  │
                └────────────────────────┘
```

A **region** contains:

- Multiple frontend clusters
- A storage cluster

One region owns the master databases. Other regions contain read-only database replicas maintained through MySQL replication.


# Fundamental Caching Pattern: Demand-Filled Look-Aside Cache

This is one of the most reusable System Design patterns in the paper.

## Read path — cache hit

```text
Web Server
     │
     │ get(k)
     ▼
 Memcache
     │
     │ HIT
     ▼
  value(v)
```

Simple and fast.


## Read path — cache miss

```text
Web Server
     │
     │ 1. get(k)
     ▼
 Memcache
     │
     │ MISS
     ▼
Web Server
     │
     │ 2. SELECT...
     ▼
 Database
     │
     │ value(v)
     ▼
Web Server
     │
     │ 3. set(k,v)
     ▼
 Memcache
```

The application populates the cache **on demand**.

The database remains authoritative.


# Write Path

Facebook does something important here.

It does **not update the cached value**.

Instead:

```text
Web Server
     │
     │ UPDATE
     ▼
 Database
     │
     │ success
     ▼
Web Server
     │
     │ delete(k)
     ▼
 Memcache
```

Why delete rather than update?

Because:

> **Deletes are idempotent.**

Memcache is not the authoritative source, so throwing away the cached copy is safe; the next read can reconstruct it from persistent storage.

### Interview mental model

```text
WRITE:

Database first
     ↓
Invalidate cache
     ↓
Next read repopulates cache
```

rather than:

```text
Database
   +
Update every cached copy
```


# Why Separate Cache and Persistent Storage?

This was an intentional architecture decision.

```text
                  Application
                 /           \
                ▼             ▼
           Memcache         Database
              │                │
          Scale cache       Scale storage
        independently       independently
```

Facebook explicitly identifies this as one of its major lessons:

> Separating cache and persistent storage allows each to scale independently.

This is a highly reusable System Design principle.


# Distributed Key Placement

Within a cluster, cached items are distributed among memcached servers using:

> **Consistent hashing.**

```text
                   key
                    │
                    ▼
             Consistent Hash
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
    Cache 1      Cache 2      Cache N
```

But this creates the next major problem.

A page may require hundreds of independent keys.

Therefore:

```text
                     Web Server
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
          Cache 1     Cache 2     Cache 3
             │           │           │
          Cache 4     Cache 5   ... Cache N
```

All web servers communicate with many memcached servers.

That creates an **all-to-all communication pattern** and introduces:

- Network congestion
- Hot servers
- Incast
- Tail latency


# Client-Side Intelligence

Facebook deliberately keeps memcached servers simple.

Instead, substantial complexity lives in the client.

```text
                    Memcache Client
                          │
         ┌────────────────┼─────────────────┐
         │                │                 │
         ▼                ▼                 ▼
    Serialization     Compression       Routing
         │                │                 │
         ├────────── Batching ──────────────┤
         │                                  │
         └──── Error Handling / Config ─────┘
```

Clients maintain a map of available servers.

The logic can exist as:

1. An application library
2. A standalone proxy called **mcrouter**

`mcrouter` exposes a memcached-server interface while routing requests to the appropriate backend servers.


# Why Put Complexity in Stateless Clients?

This is an important architectural choice.

```text
Smart Client
     │
     ▼
Simple Memcached Server
```

instead of:

```text
Simple Client
     │
     ▼
Complex Stateful Cache Server
```

The benefit is operational simplicity.

Facebook explicitly says keeping clients stateless:

- Enables rapid iteration
- Simplifies software deployment
- Keeps memcached focused on high performance

This principle reappears in the paper's conclusion:

> Stateful components are operationally more complex than stateless components.


# Parallel Requests + Batching

A web request may need hundreds of cached values.

Sequential retrieval would be disastrous:

```text
get A → wait
get B → wait
get C → wait
get D → wait
...
```

Facebook represents data dependencies as a **DAG**.

```text
                    Request
                       │
                ┌──────┴──────┐
                ▼             ▼
                A             B
             /  |  \        /   \
            ▼   ▼   ▼      ▼     ▼
            C   D   E      F     G
```

Independent requests execute concurrently.

The paper reports average batches of:

> **24 keys per request**

with p95 around **95 keys**.

This reduces network round trips.


# UDP vs TCP

This is one of the most interview-worthy decisions.

Facebook uses:

```text
GET
 │
 ▼
UDP

SET / DELETE
 │
 ▼
TCP through mcrouter
```

## Why UDP for GET?

GET is latency sensitive.

UDP avoids:

- Connection setup
- Large numbers of persistent connections
- Connection management overhead

Production measurements showed UDP could reduce request-serving latency by around:

> **20%**.


# But UDP Isn't Reliable

Exactly.

Facebook accepts this.

At peak load:

> **0.25% of get requests were discarded.**

Around 80% were late/dropped packets; the rest were out-of-order.

Instead of implementing reliable UDP:

```text
UDP failure
     │
     ▼
Treat as cache miss
```

And importantly, after this error the web server avoids inserting the retrieved result back into memcache, because the cache/network might already be overloaded.

That's a subtle but excellent overload-protection decision.


# Why TCP for SET and DELETE?

Those operations change state.

Facebook wants confirmation that they succeeded.

Therefore:

```text
Read:
failure ≈ cache miss
       ↓
UDP acceptable


Mutation:
must know outcome
       ↓
TCP
```

SET and DELETE go through local mcrouter over TCP.


# Incast Congestion

Suppose a web server requests hundreds of keys simultaneously:

```text
Cache 1 ─────┐
Cache 2 ─────┤
Cache 3 ─────┤
Cache 4 ─────┼────► Web Server
Cache 5 ─────┤
...          │
Cache N ─────┘
```

If all responses arrive simultaneously, switches or the receiving machine can become overwhelmed.

Facebook uses a **sliding window** controlling the number of outstanding memcache requests.

Conceptually:

```text
Window = N

Send N requests
     │
     ▼
Receive response
     │
     ▼
Send next request
```

The window grows on successful requests and shrinks when requests go unanswered.

This creates an important trade-off:

```text
Window too small
      ↓
Requests become serialized
      ↓
Higher latency


Window too large
      ↓
Incast congestion
      ↓
Cache errors
      ↓
Database fallback
      ↓
Even higher latency/load
```

The correct operating point is between those extremes.


# Leases: Solving Two Problems at Once

Facebook introduced **leases** to solve:

1. Stale sets
2. Thundering herds


# Problem 1 — Stale Set

Imagine:

```text
Client A                      Client B

cache miss

DB read → old V1

                              UPDATE DB → V2

                              delete cache

set cache → V1
```

Now V1 has been inserted **after V2 exists**.

The cache becomes stale.


# Lease Solution

On a cache miss:

```text
Client
   │
   │ get(k)
   ▼
Memcached
   │
   │ MISS
   │
   └────► Lease Token
             64-bit
             bound to k
```

Client queries the database and then:

```text
set(k, value, lease-token)
```

Memcached validates the token.

If a delete happened meanwhile:

```text
Delete(k)
   │
   ▼
Invalidate lease
   │
   ▼
Old client tries set
   │
   ▼
REJECT
```

Thus an old database read cannot overwrite the newly invalidated cache state.


# Problem 2 — Thundering Herd

Suppose one popular cache key expires:

```text
                 Cache miss
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
   Client 1       Client 2      Client N
       │             │             │
       └─────────────┼─────────────┘
                     ▼
                  DATABASE
```

Potentially thousands of clients hit the backend simultaneously.

Facebook's lease mechanism rate-limits lease issuance:

> By default, only **one lease token per key every 10 seconds**.

Other clients are instructed to wait briefly.

```text
First Client
     │
     ▼
Gets Lease
     │
     ▼
Database
     │
     ▼
Populate Cache


Other Clients
     │
     ▼
WAIT
     │
     ▼
Retry
     │
     ▼
Cache HIT
```

The measured impact is dramatic:

| Configuration | Peak DB queries |
|---|---:|
| Without leases               | 17K/sec  |
| With leases                  | 1.3K/sec |

That's roughly a **13× reduction in peak backend query rate**.


# Serving Stale Values

Facebook goes one step further.

When data is deleted from cache, the old value can temporarily be stored separately.

Then a GET may return:

```text
Fresh value
      OR
Stale value
      OR
Lease
```

Applications that tolerate slightly stale information can use the stale value rather than wait for the database.

The paper notes that cached values often behave like monotonically increasing snapshots, allowing many applications to use stale values without modification.

This reveals a major design philosophy of the system:

> **Freshness is a tunable engineering parameter, not an absolute requirement.**


# Memcache Pools

Different cached data behaves differently.

For example:

```text
                    Cache Workloads

          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
      High churn      Low churn     Expensive miss
```

Putting everything into one cache causes interference.

Example:

- High-churn objects constantly enter and leave.
- Valuable low-churn objects get evicted.
- Cache hit rate decreases.

Facebook therefore divides memcached servers into **pools**.

```text
                   Memcache Cluster
                         │
          ┌──────────────┼───────────────┐
          ▼              ▼               ▼
       Wildcard         App          Replicated
         Pool           Pool            Pool
                         │
                         ▼
                    Regional Pool
```

The default pool is called **wildcard**.

Separate pools isolate workloads according to:

- Access frequency
- Churn
- Item size
- Cache-miss cost
- QoS requirements


# Replication vs Partitioning

A particularly interesting decision occurs for very hot, small datasets.

Suppose:

```text
100 objects
500K requests/sec server capacity
Each request asks for all 100 objects
```

If we partition:

```text
Server A → 50 keys
Server B → 50 keys

Every request must hit BOTH servers.
```

At 1M requests/sec:

```text
A receives 1M requests
B receives 1M requests
```

Partitioning did not reduce request rate.

Instead, replicate:

```text
Server A → all 100 keys
Server B → all 100 keys

              Client
               / \
              /   \
             ▼     ▼
             A OR  B
```

Now requests can be load-balanced:

```text
A → 500K requests/sec
B → 500K requests/sec
```

So Facebook replicates when:

1. Applications fetch many keys together.
2. Dataset fits on one or two servers.
3. Request rate exceeds one server's capacity.

### Interview lesson

> **Partitioning reduces data per server. Replication can reduce requests per server.**

That's an excellent distinction to remember.


# Handling Cache Server Failures: Gutter

Cache failure is dangerous because:

```text
Cache Server Failure
       ↓
Cache misses
       ↓
Database traffic spikes
       ↓
Database overload
       ↓
More failures
       ↓
Cascading failure
```

Facebook created a special fallback pool called:

> **Gutter**

Gutter is approximately **1% of the memcached servers in a cluster**.


# Gutter Flow

```text
Client
   │
   │ GET(k)
   ▼
Normal Cache
   │
   │ No response
   ▼
Client assumes failure
   │
   ▼
Gutter
   │
   ├── HIT → return
   │
   └── MISS
        │
        ▼
     Database
        │
        ▼
   Populate Gutter
```

Gutter entries expire quickly.

This avoids having to propagate invalidations into Gutter.


# Why Not Rehash Keys to Remaining Servers?

The obvious solution after a server failure is:

```text
Failed Server
     ↓
Rehash its keys
     ↓
Remaining servers
```

Facebook explicitly avoids this.

Why?

Access distribution isn't uniform.

A single key can represent:

> **20% of one server's requests.**

Moving that key onto another already-loaded server could overload the second server:

```text
Server A fails
      │
      ▼
Hot key → Server B
            │
            ▼
       B overloaded
            │
            ▼
       B fails
            │
            ▼
        Cascade
```

Gutter instead sends this emergency traffic to otherwise idle capacity.


# Gutter Results

The production numbers are strong:

- **99% reduction in client-visible failures**
- **10–25% of failures converted into Gutter hits daily**
- When a memcached server completely fails:
  - Gutter hit rate >35% within 4 minutes
  - Often approaches 50%

This is a classic **load-shedding / fallback isolation** design pattern.


# Scaling From Cluster → Region

Eventually simply adding servers to one cluster stops being attractive.

Why?

```text
More Web Servers
       ↓
More demand on hot keys

More Cache Servers
       ↓
More all-to-all communication
       ↓
More incast
```

Facebook therefore creates multiple **frontend clusters**.

```text
                       REGION

                   Storage Cluster
                      Database
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
    Frontend C1     Frontend C2    Frontend C3
          │              │              │
     Web + Cache     Web + Cache    Web + Cache
```

This gives:

- Smaller failure domains
- More manageable networking
- Reduced incast

But introduces replication.


# Regional Cache Invalidation

The storage cluster contains the authoritative data.

Each frontend cluster may independently cache that data.

Therefore database changes must invalidate cached copies.

Facebook's Figure 6 shows the pipeline:

```text
                     UPDATE
                       │
                       ▼
                     MySQL
                       │
                       ▼
                  Commit Log
                       │
                       ▼
                    mcsqueal
                       │
                  batch deletes
                       │
             ┌─────────┼─────────┐
             ▼         ▼         ▼
         mcrouter   mcrouter   mcrouter
             │         │         │
             ▼         ▼         ▼
          Cache C1  Cache C2  Cache C3
```

SQL statements modifying authoritative state include the memcache keys that should be invalidated after commit.

A daemon called **mcsqueal** reads committed SQL operations, extracts invalidations, and broadcasts them to frontend clusters.


# Why mcsqueal Instead of Web Servers Broadcasting Deletes?

Two important reasons.

### 1. Batching

If every database communicated independently with every cache:

```text
Many DBs × Many caches
        ↓
Huge packet rate
```

mcsqueal batches deletes before sending them to mcrouter.

Result:

> **18× improvement in median deletes per packet.**

### 2. Reliability / replayability

The invalidation is connected to the database's committed log.

Therefore if invalidations are lost or misrouted, they can be replayed rather than requiring disruptive cache restarts.


# Regional Pools

Replicating every cached object across every frontend cluster wastes memory.

Facebook therefore asks:

> **Should this object be replicated per cluster, or cached only once per region?**

```text
                       Object

             Is it frequently accessed?
                    /         \
                  YES          NO
                  /             \
                 ▼               ▼
        Per-cluster cache    Regional Pool
```

Crossing cluster boundaries has costs:

- Higher latency
- About **40% less average available bandwidth** than within a cluster

So replication trades:

```text
MORE REPLICATION
      │
      ├── + Lower latency
      ├── + Less cross-cluster bandwidth
      ├── + Better fault tolerance
      └── - More memory
```

Regional pools trade:

```text
LESS REPLICATION
      │
      ├── + Memory efficiency
      └── - Cross-cluster network traffic
```

The decision is based on:

- Access rate
- Dataset size
- Number of unique users


# Cold Cluster Warmup

Suppose Facebook brings up a new frontend cluster:

```text
New Cluster
    │
    ▼
Empty Cache
    │
    ▼
Massive miss rate
    │
    ▼
Database overload
```

Instead of loading misses from persistent storage:

```text
Cold Cluster
      │
      │ cache miss
      ▼
Warm Cluster
      │
      ▼
existing cached value
```

This is **Cold Cluster Warmup**.

It reduces time to full capacity from:

> **a few days → a few hours.**


# Cold Cluster Race Condition

But consider:

```text
Cold Cluster                  Warm Cluster

DB updated → V2

                              still contains V1

cold cache miss
       │
       └─────────────────────► returns V1

cache V1 forever
```

Facebook mitigates this with a **two-second delete hold-off**.

A recent delete prevents an `add` from immediately reinserting potentially stale data.

If the add fails:

```text
Client
   │
   ▼
Refetch database
```

The paper acknowledges that this is not theoretically perfect—an invalidation could be delayed beyond two seconds—but accepts the rare inconsistency because the operational benefit is much larger.

This is a very important example of pragmatic engineering.


# Scaling Region → Multiple Regions

Now the architecture becomes:

```text
                         MASTER REGION
                              │
                         Master MySQL
                              │
                    Replication Stream
                    ┌─────────┴─────────┐
                    ▼                   ▼
              Replica Region A    Replica Region B
                    │                   │
               Read Replica        Read Replica
                    │                   │
                 Memcache            Memcache
```

Advantages:

- Lower latency by moving infrastructure closer to users
- Geographic fault isolation
- Protection against large disasters/power failures
- Economic advantages of additional locations

But the main problem becomes:

> **Replica lag.**


# Consistency Model

This is essential.

Facebook does **not** attempt strong global consistency.

The paper says the system provides:

> **Best-effort eventual consistency, emphasizing performance and availability.**

So unlike the previous Spanner paper:

```text
Spanner
   │
   └── External consistency
       through Paxos + TrueTime
```

this paper's architecture intentionally occupies a different design point:

```text
Facebook Memcache
        │
        └── Best-effort eventual consistency
             │
             ├── Performance
             └── Availability
```

That contrast is useful conceptually, though the statement about Facebook's choice itself comes directly from this paper.


# The Multi-Region Race

Imagine:

```text
MASTER                         REPLICA

DB = V1                        DB = V1
Cache = V1                     Cache = V1

UPDATE V2
   │
   ▼
Delete cache
   │
   │ invalidation
   └──────────────────────────► delete cache

                               cache miss
                                   │
                                   ▼
                               Replica DB
                                   │
                               still V1!
                                   │
                                   ▼
                              cache V1 again
```

The problem:

> Cache invalidation can arrive before database replication.

Facebook avoids sending replica-region invalidations directly from the web server.

Instead, invalidations flow through the storage/replication infrastructure so their ordering better matches database replication.


# Non-Master Writes: Remote Markers

Suppose a user is served from India/Asia-style replica region conceptually, while the master is remote.

The user updates profile data.

```text
Replica Region
      │
      │ write
      ▼
Master Region
      │
      ▼
Database updated
```

But replication hasn't caught up yet.

The user's next read could hit:

```text
Local Replica DB → OLD VALUE
```

Facebook introduces **remote markers**.


# Remote Marker Flow

For key `k`:

```text
1. Set remote marker rk

2. Write k to master DB

3. Delete k from local cache
```

Then a subsequent read:

```text
             GET(k)
                │
                ▼
           Cache miss
                │
                ▼
         Does rk exist?
           /        \
         YES         NO
         /            \
        ▼              ▼
 Query Master      Query Local
   Region           Replica
```

The marker means:

> **The local replica may be stale.**

Therefore the request goes to the master.

Once replication catches up and the invalidation removes the marker, local reads become safe again.


# The Trade-off

Remote markers intentionally trade:

```text
Extra WAN latency
       ↓
Query master
```

for:

```text
Lower probability
of stale reads
```

This is exactly the kind of reasoning interviewers want to hear.


# Single-Server Optimizations

Facebook didn't solve scaling purely by adding machines.

The paper also optimizes each memcached instance.

Initial improvements included:

```text
Original
single-threaded memcached
       │
       ▼
Expandable hash table
       │
       ▼
Multi-threading
       │
       ▼
Per-thread UDP ports
       │
       ▼
Fine-grained locking
```


# Fine-Grained Locking

Moving away from one global lock dramatically increased throughput.

| Workload | Before | After |
|---|---:|---:|
| Cache hits          | 600K items/sec | **1.8M/sec** |
| Cache misses        | 2.7M/sec       | **4.5M/sec** |

Fine-grained locking therefore tripled peak hit throughput.


# Multiget

Batching multiple keys into one request also provides major benefits.

The paper reports approximately:

> **4× throughput improvement for 10-key multigets compared with single gets.**

Why?

```text
10 single gets
      ↓
Many packets


1 multiget
      ↓
Fewer packets
      ↓
Less network overhead
```


# Adaptive Slab Allocator

Memcached divides memory into slab classes.

```text
Memory
 │
 ├── 64-byte chunks
 ├── ~68-byte chunks
 ├── ...
 └── up to 1 MB
```

Objects go into the smallest slab class that can hold them.

Each class uses its own LRU.

The problem:

```text
Workload changes
       ↓
One slab class needs more memory
       ↓
Another has too much
       ↓
Poor hit rate
```

Facebook therefore created an **adaptive slab allocator** that periodically redistributes slabs based on eviction behavior.

Its goal is effectively to approximate a more global LRU policy across slab classes.


# Transient Item Cache

Memcached normally lazily removes expired entries.

Problem:

```text
Short-lived object expires
        │
        ▼
Still occupies memory
        │
        ▼
Waits until GET or LRU eviction
```

Facebook creates a special structure for short-lived items:

```text
               Circular Buffer

   second 1 → [items]
   second 2 → [items]
   second 3 → [items]
        ...
```

Every second:

```text
Head bucket
     ↓
Evict all expired items
     ↓
Advance
```

This reduced one key family's cache-memory consumption from:

> **6% → 0.3%**

without hurting hit rate.


# Zero/Low-Disruption Software Upgrades

Restarting memcached normally destroys its cache.

Then:

```text
Restart
   ↓
Cold cache
   ↓
DB traffic
```

A memcached server can take hours to recover hit rate, making fleet-wide upgrades slow.

Facebook therefore stores cached values and major structures in:

> **System V shared memory**

so they survive process/software upgrades.

```text
Old memcached process
        │
        ▼
Shared Memory
        │
   process restart
        │
        ▼
New memcached process
        │
        ▼
Existing cache survives
```


# Production Workload Characteristics

Understanding the workload explains many architectural choices.

## Fan-out

Across general page requests:

> 56% contact fewer than 20 memcached servers.

But popular data-intensive pages commonly access:

> **100+ distinct servers**, and several hundred isn't unusual.

This explains why:

- Batching
- Parallelism
- UDP
- Incast control

matter so much.


## Item sizes

The response-size distribution is heavily skewed:

```text
Median = 135 bytes
Mean   = 954 bytes
```

So a small number of large values pull the mean far above the median.


## Latency

Production request latency over seven days:

| Percentile | Latency |
|---|---:|
| p50               | 333 μs   |
| p75               | 475 μs   |
| p95               | 1.135 ms |

The paper attributes p95 variation partly to large responses and scheduling delays.


# Invalidation Reliability

Facebook explicitly monitors whether cache invalidations actually propagate.

For master-region invalidations:

```text
Within 1 second → four 9s
Within 1 hour   → five 9s
```

For replica-region paths:

```text
Within 1 second   → three 9s
Within 10 minutes → four 9s
```

This directly shows why cross-region consistency is harder.


# 3. Critical Engineering Trade-offs & Design Choices

## Trade-off 1 — Consistency vs Performance/Availability

Facebook explicitly chooses:

```text
Strong Consistency
       ↑
       │ not chosen
       │
       ▼
Best-effort eventual consistency
       +
High performance
       +
High availability
```

The paper says stronger semantics were often prohibitively expensive at Facebook's scale.

### Interview lesson

Consistency is not automatically "the stronger, the better."

The right question is:

> **What consistency guarantee does the product actually require, and what would stronger semantics cost?**


# Trade-off 2 — Cache Delete vs Cache Update

Facebook chooses:

```text
DB UPDATE
   ↓
CACHE DELETE
```

instead of:

```text
DB UPDATE
   ↓
CACHE UPDATE
```

because delete is:

- Idempotent
- Simpler
- Safe because cache isn't authoritative


# Trade-off 3 — UDP vs TCP

```text
GET
 │
 └── UDP
     + Lower latency
     + Less connection overhead
     - Packet loss


SET / DELETE
 │
 └── TCP
     + Reliable state change
     - More overhead
```

Instead of forcing one protocol everywhere, Facebook chooses according to operation semantics.


# Trade-off 4 — Replication vs Memory

Replication provides:

- Lower load per hot cache server
- Lower latency
- Better fault tolerance

But:

```text
Replication
    ↓
Same object stored N times
    ↓
Memory inefficiency
```

Regional pools reduce replication for large, infrequently accessed objects.


# Trade-off 5 — Replication vs Partitioning

Partitioning is not always the right answer.

For a tiny dataset where every request needs most keys:

```text
Partition
   ↓
Every request still hits every partition
```

Replication lets each request use one replica.

This is one of the paper's strongest workload-aware design decisions.


# Trade-off 6 — Availability vs Freshness

Gutter intentionally accepts:

```text
Possibly stale cache data
```

to prevent:

```text
Backend overload
     ↓
Cascading outage
```

The system treats temporary staleness as preferable to widespread failure.


# Trade-off 7 — Cold Startup Speed vs Perfect Consistency

Cold Cluster Warmup gets clusters operational in hours rather than days.

But its two-second hold-off isn't a mathematical guarantee against every possible delayed invalidation.

Facebook explicitly accepts that risk because:

> operational benefits outweigh rare cache-consistency problems.


# Trade-off 8 — Smart Client vs Smart Server

Facebook chooses:

```text
Stateless Smart Client
        +
Simple Stateful Server
```

because stateful infrastructure is harder to:

- Upgrade
- Deploy
- Debug
- Evolve

This becomes one of the paper's explicit conclusions.


# Trade-off 9 — Incast vs Parallelism

More parallel requests reduce latency only until they saturate network components.

```text
Too little concurrency
        ↓
Serialization
        ↓
Latency


Too much concurrency
        ↓
Incast
        ↓
Packet loss
        ↓
Cache miss
        ↓
DB load
```

Sliding-window flow control dynamically navigates this trade-off.


# Trade-off 10 — Cache Hit Rate vs Workload Isolation

One giant pool maximizes flexibility but creates interference.

Multiple pools provide isolation but require more operational management.

Facebook chooses pools based on workload characteristics rather than treating all cache objects equally.


# Failure Patterns to Memorize

The paper is especially useful because it contains several real failure patterns:

```text
1. CACHE MISS STORM
   → Lease

2. STALE SET
   → Lease token validation

3. SERVER FAILURE
   → Gutter

4. INCAST
   → Sliding request window

5. COLD CACHE
   → Warmup from another cluster

6. CACHE/DB RACE
   → Database-driven invalidation

7. REPLICA LAG
   → Remote marker

8. WORKLOAD INTERFERENCE
   → Separate pools

9. MEMORY MISALLOCATION
   → Adaptive slab allocator

10. RESTART CACHE LOSS
    → Shared memory
```

This list is extremely useful for System Design interviews.


# 4. High-Impact Interview Takeaways

## Takeaway 1 — Cache failure can be worse than having no cache

A cache protects your database.

Therefore:

```text
Cache Failure
     ↓
DB QPS spike
     ↓
DB overload
     ↓
System outage
```

So cache architecture must explicitly protect the backing store during cache failures.

Facebook's Gutter is the canonical example from this paper.


# Takeaway 2 — Prevent thundering herd before scaling the database

If 10,000 clients miss the same hot key, you don't want:

```text
10,000 cache misses
        ↓
10,000 DB queries
```

Instead:

```text
10,000 misses
      ↓
1 lease holder
      ↓
1 DB query
      ↓
Cache populated
      ↓
Others hit cache
```

Facebook's measured peak DB rate fell from **17K/s to 1.3K/s** for affected keys.


# Takeaway 3 — Cache invalidation should follow authoritative state

Instead of making web servers responsible for distributed invalidation:

```text
Web Server
     ↓
Maybe DB committed?
     ↓
Broadcast delete?
```

tie invalidation to the committed database operation:

```text
Database commit
      ↓
Durable log
      ↓
mcsqueal
      ↓
Invalidation
```

That gives the system a reliable source from which invalidations can be replayed.


# Takeaway 4 — Design around workload shape, not generic rules

Facebook uses:

```text
Hot small dataset
     ↓
Replication


Large cold dataset
     ↓
Regional pool


High churn
     ↓
Separate pool


Short-lived data
     ↓
Transient item cache
```

There is no universal cache-placement strategy.


# Takeaway 5 — Sometimes stale is better than unavailable

Facebook repeatedly chooses bounded/pragmatic staleness to protect latency and availability:

- Gutter
- Stale-value serving
- Cold-cluster warmup
- Best-effort eventual consistency

This is a strong System Design lesson:

> **Treat freshness as a product requirement with a cost, rather than assuming every object needs the strongest possible semantics.**


# Takeaway 6 — Scaling creates different bottlenecks at different stages

This is arguably the deepest lesson in the paper.

```text
Single Server
     ↓
CPU / locking / memory


Single Cluster
     ↓
Fan-out / latency / incast


Multiple Clusters
     ↓
Replication / memory / invalidation


Multiple Regions
     ↓
Consistency / replication lag
```

The bottleneck evolves with scale.

Your architecture should evolve with it.

### Talking Point 1 — Cache stampede

> **"For a hot-key cache miss, I wouldn't allow every client to independently hit the database. Facebook's memcache design uses leases so only a controlled client refills the key while others briefly wait, dramatically reducing thundering-herd load."**

### Talking Point 2 — Cache failure isolation

> **"A cache outage can become a database outage if every miss falls through to persistent storage. I would introduce isolated fallback cache capacity similar to Facebook's Gutter rather than immediately rehashing failed-server traffic onto already-loaded cache nodes."**

### Talking Point 3 — Multi-region consistency

> **"With asynchronous database replication, cache invalidation ordering becomes critical. If the cache is invalidated before the replica database catches up, a cache miss can refill stale data. # 5. Follow-up Deep-Dive Questions

## Principal Question 1

### "Why invalidate cache instead of updating it after a database write?"

### Ideal high-level answer

The database is authoritative; memcache isn't.

Deleting has a useful property:

> **It is idempotent.**

Therefore:

```text
UPDATE database
       ↓
DELETE cache
       ↓
Next read rebuilds value
```

Repeated deletes are harmless, whereas distributed cache updates introduce more coordination and opportunities for stale-value races.

The paper explicitly identifies idempotency as the reason for choosing delete over update.


# Principal Question 2

### "Why doesn't Facebook simply redistribute a failed cache server's keys using consistent hashing?"

### Ideal high-level answer

Because traffic isn't uniformly distributed.

A single key may account for **20% of one server's requests**.

Rehashing that hot key onto another production cache server can overload that server:

```text
A fails
  ↓
hot traffic → B
               ↓
            B fails
               ↓
             cascade
```

Instead, Gutter provides isolated spare capacity specifically for failure traffic.

That protects both:

- Remaining cache servers
- Persistent storage

The paper reports a **99% reduction in client-visible failures** from this approach.


# Principal Question 3

### "Why can a cache invalidation actually make consistency worse in a multi-region system?"

### Ideal high-level answer

Because database replication is asynchronous.

Suppose:

```text
Master DB = V2
Replica DB = V1
```

If the replica cache is immediately invalidated:

```text
Cache delete
     ↓
Next request misses
     ↓
Read replica DB
     ↓
Gets V1
     ↓
Cache V1
```

You've just repopulated the cache with stale data.

Therefore invalidation must account for the **ordering between database replication and cache invalidation**.

Facebook ties invalidation to storage infrastructure and uses remote markers for writes from non-master regions.


# Bonus Principal-Level Questions

### 4. Why use UDP for reads but TCP for writes?

Because failed GETs can safely become cache misses, while SET/DELETE operations require confirmation of state change. UDP lowers GET latency, while TCP provides reliable mutation semantics.

### 5. Why isn't partitioning always better than replication?

If requests routinely need most of a small dataset, partitioning forces every request to contact every partition. Replication allows each complete request to be served by one replica, reducing per-server request rate.

### 6. How do you prevent a thundering herd?

Issue refill leases at a controlled rate. One client fetches and repopulates the missing key while other clients wait briefly and retry.

### 7. How would you warm a new cache cluster without overwhelming the DB?

Read misses from an existing warm cluster instead of persistent storage, while using a delete hold-off mechanism to reduce stale-refill races. Facebook reduced warmup from days to hours.

### 8. Why separate cache pools?

Different key families have different churn, item sizes, access frequencies, miss costs, and QoS needs. Mixing them can cause one workload to evict useful data belonging to another.

## One-line architecture to remember

> **Facebook Memcache = demand-filled look-aside caching + intelligent stateless clients + consistent hashing + workload-aware replication/pooling + leases for stampede control + Gutter for failure isolation + database-driven invalidation + remote markers for multi-region replica lag.**

And the deepest interview lesson from the paper is:

> **Caching at massive scale isn't mainly about storing values in RAM. The difficult problems are protecting the database during misses and failures, controlling network fan-out, preventing cache stampedes, choosing replication based on workload shape, and maintaining acceptable consistency as the architecture expands from one cluster to many geographically distributed regions.**

The paper's final lessons reinforce exactly this philosophy: **independently scale cache and storage, invest in monitoring and operations as much as raw performance, prefer stateless logic where possible, support gradual rollout/rollback, and keep the system simple.**
